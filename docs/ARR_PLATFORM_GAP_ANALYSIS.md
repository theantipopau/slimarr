# *arr Platform Gap Analysis

**Date:** 2026-09-02
**Purpose:** Compare Slimarr's current architecture against patterns established by Radarr, Sonarr, Prowlarr, Overseerr/Jellyseerr (Seerr), Bazarr, Tdarr/Unmanic, Tautulli, and Recyclarr — specifically to decide what the new Recommendation & Collection Completion feature needs, not to chase feature parity for its own sake.

Every item below states **why it matters for Slimarr specifically** (not "because Radarr has it"). Three buckets, per the brief: **Implement now**, **Prepare the architecture now, implement later**, **Not appropriate for Slimarr**.

---

## Implement now

| Pattern | Source | Why Slimarr needs this now |
|---|---|---|
| **Durable, resumable background jobs for the recommendation engine** | Radarr/Sonarr's task scheduler; Tautulli's scheduled library scans | Slimarr already has this (`core/jobs.py` — see audit §1/§4). "Implement now" here means *use the existing system* for `recommendation_refresh`, `streaming_availability_refresh`, and `collection_completion_scan` job kinds, not build a new one. |
| **Explicit service/repository boundaries for the new domain** | Radarr's `NzbDrone.Core` layering (indexers/download clients/quality behind interfaces) | The recommendation engine is a genuinely new domain (candidates, scoring, reasons, feedback) that should not be bolted onto `core/comparer.py` or `api/system.py`. New code lives in `backend/core/recommendations/` (scoring, sourcing, streaming-availability) and `backend/api/recommendations.py`, mirroring the existing `core/` + `api/` split rather than inventing a new layout. |
| **Idempotent, deduplicated candidate generation** | Sonarr's import-list dedup logic | A collection-completion scan that runs nightly must not create a second `RecommendationCandidate` row for a title it already surfaced last week. Unique constraint on `(media_type, external_id_namespace, external_id)` in the candidate table, enforced at the DB level, not just in application logic. |
| **Stable reason codes, not free-text-only explanations** | Radarr's Custom Format scoring (each match has a name + weight, shown in the UI) | The brief explicitly requires "structured reasons" and forbids a generic "AI recommended this" explanation. A `RecommendationReason` row with a stable `reason_code` (e.g. `missing_collection_member`, `direct_sequel`, `streaming_available`) plus a human-readable string is the direct analog of Radarr's Custom Format match display, and is required for the deterministic-scoring/explainability requirement regardless of AI. |
| **Capability detection before calling an optional integration action** | Radarr/Sonarr degrade gracefully when an indexer doesn't support an feature; Seerr's own API has diverged from legacy Overseerr | The brief explicitly requires this for Seerr hand-off ("perform capability detection... disable the action gracefully"). Given audit finding A4 (Slimarr's existing "capability" dict is currently a static placeholder, not real detection), this is a chance to build the pattern correctly the first time for the Seerr/Radarr/Sonarr hand-off actions, rather than copying the existing placeholder pattern. |
| **Structured, componentized health reporting** | Radarr/Sonarr's System → Status page; Tautulli's dashboard health widgets | Slimarr already has `/system/health/matrix` distinguishing several integrations. Extending it to also report recommendation-provider state (TMDB reachable, streaming-availability cache freshness, AI provider reachable if enabled) is a natural, low-risk extension of an existing pattern — not a new subsystem. |
| **Rate limiting on expensive rebuild/refresh operations** | Prowlarr's indexer rate-limit handling; Radarr's RSS sync interval floor | The brief requires this explicitly for recommendation rebuilds. Slimarr already has an analogous pattern for automation cycles (`schedule.min_cycle_interval_minutes` cooldown in `orchestrator.run_full_cycle`) — the recommendation refresh job reuses the same cooldown-gate shape. |

## Prepare the architecture now, implement later

| Pattern | Source | Why not now, but why prepare |
|---|---|---|
| **Per-user settings / permissions** | Radarr v5's forms auth + optional multi-user; Seerr's request-approval permission model | Slimarr's `User` model is single-account with no roles (confirmed in audit §1). Building real multi-user permissions is a significant, separate undertaking with its own migration and auth implications that would balloon this release's scope. **Prepare for it**: the new `Recommendation`/`RecommendationFeedback` tables include a `user_scope` column now (defaulting to a single implicit scope value for the one existing user) so a future multi-user migration doesn't require a schema rewrite, but no UI or enforcement for multiple users ships in this release. |
| **Notification agents (Discord/webhook/etc.)** | Radarr/Sonarr's notification connections; Tautulli's notification agents | Useful eventually ("a new recommendation matched your criteria"), but it's an orthogonal feature to the recommendation engine itself and the brief doesn't require it. Prepare by emitting a `recommendation:created`-class Socket.IO event (mirroring the existing event taxonomy in `realtime/events.py`) that a future notification-agent system can subscribe to, without building the agents themselves now. |
| **Versioned API contracts** | Radarr's `/api/v3` (with legacy `/api` still routable) | Slimarr's API has no version negotiation beyond the `/api/v1` prefix baked into every route already. The new recommendation routes ship under the existing `/api/v1` prefix (additive, no breaking change) rather than introducing `/api/v2` for one feature — but response models are designed so a future breaking change to recommendation shapes wouldn't require touching unrelated `/api/v1` routes, since they live in their own router/model modules. |
| **Backup and restore** | Radarr/Sonarr's System → Backup | Genuinely useful, but unrelated to the recommendation feature and would touch the whole DB, not just new tables. Out of scope for this pass; noted for a future release. |
| **Centralized secret-redaction logging sink** | — (general good practice, not *arr-specific) | Per audit finding A6, redaction today is applied per call site. The new AI-provider integration is exactly the kind of code that must never leak a prompt or API key to logs — it will call the *existing* `redact_text`/`redact_url` helpers explicitly at every log call site in this release (not a new sink), but a proper logging-filter-level fix remains a documented follow-up rather than being done incidentally here. |
| **Quality-profile-style reusable configuration objects** | Radarr's Quality Profiles (named, reusable, referenced by movies) | The brief asks for a long list of recommendation config knobs (region, providers, genres, languages, minimum score, etc.). For v2.0.0 these live as flat fields on a single `RecommendationSettings`-style config section (matching Slimarr's existing single-config-object convention in `config.py`), not as a named/reusable "profile" system — that's more complexity than a single-user app needs today. If per-category profiles (e.g. different rules for movies vs. TV) become necessary later, the config section is structured so it can be split without a breaking change. |

## Not appropriate for Slimarr

| Pattern | Source | Why it doesn't fit |
|---|---|---|
| **Rebuilding Seerr's full request/approval workflow inside Slimarr** | Overseerr/Jellyseerr | The brief is explicit about this: "Do not rebuild a complete request-management platform inside Slimarr." Slimarr's Seerr action is a thin, capability-checked hand-off, not a competing implementation. |
| **Torrent/indexer-protocol expansion** | Prowlarr's broader protocol support | Slimarr is Usenet-first by product identity (confirmed in prior roadmap work); the recommendation feature's "send to Radarr/Sonarr" hand-off deliberately leaves acquisition to those tools, which already handle whatever protocols the user has configured. No reason for Slimarr itself to grow protocol support. |
| **Media transcoding / optimization queues** | Tdarr / Unmanic | Slimarr's identity is "replace with a smaller existing release," not "re-encode." Nothing in the recommendation feature touches transcoding, and adding it would blur a boundary the project has held deliberately (per prior roadmap: "Slimarr replaces, it does not encode"). |
| **Recyclarr-style repeatable config-sync from a remote TRaSH-Guides-like source** | Recyclarr | Slimarr's comparison/quality config is already a single flat, user-owned config section (`comparison:` in `config.yaml`) with no community-maintained preset ecosystem behind it the way Radarr/Sonarr Custom Formats have. Introducing a sync-from-remote-repo pattern for a single-app config section this size isn't proportionate. |
| **Full multi-tenant permission system in this release** | Seerr's per-user request quotas/permissions | Covered above as "prepare, don't implement" — full implementation now would require a parallel auth overhaul unrelated to recommendations and is explicitly out of proportion for this release given the audit's finding that the current model is genuinely single-user end to end. |

---

## Net architectural takeaway

Slimarr's foundations are closer to "mature *arr-adjacent app" than the brief's framing might suggest — the persistent job system, structured health matrix, storage-operation audit log, and decision-audit log are all real, tested infrastructure that a from-scratch recommendation feature in a less mature codebase would have to build from nothing. The gaps that matter for *this* feature are narrow and specific (no per-user scope, no capability-detection-that-actually-detects-anything, no shared HTTP client for the integrations the new feature will use most) rather than structural. The plan in `docs/RECOMMENDATION_ARCHITECTURE.md` builds on the existing job/event/health infrastructure rather than replacing any of it.
